# ADR-0001: API 핸들러 파이프라인으로 크로스커팅 로직 중앙화

- 상태: 채택 (2026-08)
- 관련 코드: `lib/server/api-handler.ts`, `app/api/**/route.ts`

## 컨텍스트

라우트 12개가 각자 레이트 리밋 → 인증 → JSON 파싱 → 필드 검증 → try/catch →
에러 JSON 생성을 손으로 반복하고 있었다. 복붙 드리프트가 실제로 발생했다:
`push/subscribe`에는 레이트 리밋이 아예 없었고, 에러 응답 형태와 로깅 방식이
라우트마다 제각각이었다.

## 결정

`createApiHandler(config)` 하나로 크로스커팅 스택을 선언적으로 조립한다.
라우트는 정책(레이트 리밋 수치, 인증 모드, body 스키마)을 선언하고
도메인 로직만 `handler(ctx)`에 구현한다.

파이프라인 순서: requestId 발급 → 레이트 리밋 → 인증(세션/Bearer) →
body 파싱+검증 → query 검증 → 핸들러 → 에러 매핑 → 완료 로그(+durationMs).

핵심 제약: **기존 응답 계약은 바이트 단위로 보존**한다. 레거시 메시지 문자열
("invalid json", "로그인이 필요합니다." 등)은 라우트별 설정으로 주입하고,
새 필드(`code`, `requestId`)는 추가만 한다 — 추가 필드는 non-breaking.

## 결과

- 신규 라우트는 남용 방어·관측성·에러 일관성을 공짜로 얻는다 (기본값이 안전).
- 파이프라인 자체를 단위 테스트 한 번으로 검증한다 (`tests/api-handler.test.ts`).
- 트레이드오프: 간단한 라우트에도 약간의 간접 계층이 생긴다. Express/NestJS의
  미들웨어/인터셉터와 같은 개념이므로 프레임워크를 옮겨도 사고방식은 이식된다.
